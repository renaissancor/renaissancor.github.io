# 네트워크 I/O 모델 0편 — 준비됐다고 알려줄까, 끝났다고 알려줄까

`select`, `poll`, `epoll`, `io_uring`, IOCP, RIO. 서버를 만들다 보면 반드시 마주치는 이름들인데, 따로따로 외우면 금방 섞인다. 이 시리즈는 이 API들을 **두 갈래의 한 계보**로 묶어서 설명한다. 0편에서는 그 두 갈래가 무엇이고 왜 갈라졌는지만 다룬다.

---

## 출발점: 연결 1만 개를 어떻게 기다릴까

서버가 하는 일의 대부분은 **기다리는 것**이다. 클라이언트 1만 명이 접속해 있어도, 어느 순간 실제로 데이터를 보내는 건 그중 일부다. 문제는 "누가 보냈는지 어떻게 아느냐"다.

### 1단계 — Blocking I/O: 연결마다 스레드 하나

```cpp
// 연결 하나를 맡은 스레드
for (;;) {
    ssize_t n = recv(fd, buf, sizeof buf, 0);   // 데이터가 올 때까지 여기서 잠든다
    handle(buf, n);
}
```

가장 단순하다. `recv`는 데이터가 올 때까지 스레드를 재우고, 오면 깨운다. 연결 하나에 스레드 하나를 붙이면 끝이다.

그런데 연결이 1만 개면 스레드도 1만 개다.

- 스레드마다 스택이 있다. 기본 수 MB를 예약하니, 1만 개면 가상 메모리만 수십 GB다.
- 깨어날 스레드를 고르고 바꾸는 **컨텍스트 스위칭** 비용이 연결 수에 비례해서 늘어난다.
- 대부분의 스레드는 대부분의 시간 동안 **아무것도 안 하고 잠들어 있다.** 자원을 기다리는 데 쓰는 셈이다.

### 2단계 — Non-blocking + 반복 확인: 계속 물어보기

소켓을 non-blocking으로 바꾸면 `recv`는 데이터가 없을 때 잠들지 않고 바로 `EAGAIN`을 돌려준다. 그러면 스레드 하나로 1만 개를 돌아가며 물어볼 수 있다.

```cpp
for (;;)
    for (int fd : all_fds)                       // 1만 번
        if (recv(fd, buf, sizeof buf, 0) > 0)    // 대부분 "없음"
            handle(buf);
```

스레드 문제는 사라졌지만, 이번에는 **데이터가 없는 소켓에도 매번 시스템 콜을 한다.** 1만 번 물어서 3번 데이터가 있으면, 9,997번의 커널 왕복은 순수한 낭비다. CPU는 100%인데 일은 거의 안 한다.

### 그래서: 커널에게 "알려달라"고 하자

결국 필요한 건 이것이다.

> 내가 일일이 묻지 않아도, **무슨 일이 생기면 커널이 알려줘.**

여기서 길이 **두 갈래로 갈라진다.** "무슨 일"을 무엇으로 정의하느냐의 차이다.

## 두 갈래: Readiness와 Completion

### 식당 비유

음식을 주문하고 기다리는 상황을 떠올려 보자.

- **Readiness (준비 통지)** — 진동벨을 받는다. 벨이 울리면 "음식 나왔으니 **가지러 오세요**"라는 뜻이다. 내가 카운터까지 가서 직접 받아와야 한다.
- **Completion (완료 통지)** — 테이블 번호를 알려준다. 직원이 **테이블까지 차려놓고** "다 됐습니다"라고 알려준다. 나는 먹기만 하면 된다.

### 코드로 보면

**Readiness 모델** — "이 소켓, 지금 읽으면 안 막혀"를 알려준다.

```cpp
// 1. 기다린다: "누가 읽을 준비가 됐나?"
int n = epoll_wait(ep, events, 64, -1);
for (int i = 0; i < n; ++i) {
    // 2. 알림을 받은 뒤에 내가 직접 읽는다 (여기서 복사가 일어남)
    recv(events[i].data.fd, buf, sizeof buf, 0);
}
```

**Completion 모델** — "이 버퍼에 읽어놔. 끝나면 알려줘"라고 미리 맡긴다.

```cpp
// 1. 미리 맡긴다: "이 소켓에서 이 버퍼로 읽어줘"
submit_recv(fd, buf, sizeof buf);
// 2. 기다린다: "끝난 거 있나?"
completion c = wait_completion();
// 3. 이미 buf에 데이터가 들어와 있다. 바로 쓴다.
handle(buf, c.bytes);
```

### 무엇이 달라지나

| | Readiness | Completion |
|---|---|---|
| 커널이 알려주는 것 | "지금 하면 안 막힌다" | "다 했다" |
| 실제 복사는 누가 | **내가** 알림 뒤에 `recv`를 불러서 | **커널이** 미리 맡긴 버퍼에 |
| 작업당 시스템 콜 | 기다리기 + `recv` + `send` | 맡기기와 기다리기를 **묶어서** 한 번에 가능 |
| 버퍼 소유권 | 내 것. `recv`를 부르는 순간에만 쓰임 | **완료될 때까지 커널 것.** 그 전에 해제하면 사고 |
| 대표 API | `select`, `poll`, `epoll` (Linux), `kqueue` (BSD/macOS) | IOCP, RIO (Windows), `io_uring` (Linux) |

표의 네 번째 줄이 completion 모델에서 가장 흔한 버그의 원인이다. 버퍼를 커널에 맡겨놓고 완료를 받기 전에 그 버퍼를 지우거나 재사용하면, 커널이 이미 해제된 메모리에 데이터를 써버린다. IOCP를 써본 사람이라면 `OVERLAPPED` 구조체와 버퍼의 수명 관리에서 한 번쯤 데어봤을 것이다.

## 시리즈 내내 쓸 두 가지 비용

API를 비교할 때 "빠르다/느리다" 대신 **비용 두 개**로 나눠서 보면 훨씬 명확해진다.

1. **유휴 연결 비용** — 연결은 되어 있지만 **아무것도 안 보내는** 소켓 하나가, 매번 기다릴 때마다 드는 비용
2. **활성 연결 비용** — 실제로 데이터가 오가는 소켓 하나를 처리하는 데 드는 비용 (주로 시스템 콜 횟수)

이 두 비용을 기준으로 보면 Linux의 계보가 한 줄로 정리된다.

| API | 유휴 연결 비용 | 활성 연결 비용 |
|---|---|---|
| `select` / `poll` | **있음** — 매번 전체 목록을 커널에 넘기고 전부 확인 | 시스템 콜 2–3번 |
| `epoll` | **없음** — 준비된 것만 돌려줌 | 시스템 콜 2–3번 |
| `io_uring` | 없음 | **줄어듦** — 여러 작업을 한 번의 시스템 콜로 묶음 |

`epoll`은 **유휴 비용**을 없앴고, `io_uring`은 **활성 비용**을 줄였다. 서로 다른 비용을 줄인 서로 다른 단계다. 이걸 구분하지 않으면 "`io_uring`이 `poll`보다 100배 빠르다" 같은 비교가 나오는데, 그 차이의 대부분은 `io_uring`이 아니라 20년도 더 전에 `epoll`이 이미 해결한 것이다.

Windows 쪽도 비슷한 구도다. `select`는 Linux와 같은 문제를 갖고 있고, IOCP는 처음부터 completion 모델로 설계됐다. RIO는 IOCP의 활성 비용을 더 줄이려고 나왔다. `io_uring`이 Linux에서 하려는 일과 같은 방향이다.

## 연표

| 연도 | 사건 |
|---|---|
| 1983 | `select` (4.2BSD) |
| 1994 | IOCP (Windows NT 3.5) |
| 1997 | `poll` 시스템 콜 (Linux 2.1) |
| 1999 | Dan Kegel, "The C10K problem" — 연결 1만 개 문제의 정리 |
| 2000 | `kqueue` (FreeBSD 4.1) |
| 2002 | `epoll` (Linux 2.5.44) |
| 2012 | RIO (Windows 8 / Server 2012) |
| 2019 | `io_uring` (Linux 5.1) |

Windows는 1994년부터 completion 모델이 있었고, Linux는 readiness 모델로 오래 버티다가 2019년에야 제대로 된 completion 모델을 얻었다. 이 비대칭이 두 플랫폼의 서버 설계 문화를 꽤 다르게 만들었다. 시리즈 중간에 다시 다룬다.

## 시리즈 지도

이 시리즈는 블로그의 분류 원칙을 따라 세 섹션에 나뉘어 있다. 플랫폼과 무관한 개념(이 글과 마지막 측정 편)은 **Operating Systems**에, 각 API의 동작 방식은 **Linux Systems**와 **Windows Systems**에 있다.

| 편 | 주제 | 위치 | 한 줄 요약 |
|---|---|---|---|
| 0 | 개요 (이 글) | Operating Systems · `os-05` | readiness와 completion, 유휴 비용과 활성 비용 |
| 1 | `select` | Linux Systems · `linux-01`, Windows Systems · `win-07` | 목록 하나로 전부 넘기기. Linux는 비트맵에 1024개, Windows는 소켓 배열에 기본 64개. Windows 편은 WSAAsyncSelect와 WSAEventSelect까지 |
| 2 | `poll` | Linux Systems · `linux-02` | 개수 제한은 사라졌지만 매번 전부 복사하고 전부 확인 |
| 3 | `epoll` | Linux Systems · `linux-03` | 관심 목록을 커널에 남겨두고, 준비된 것만 받기 |
| 4 | IOCP | Windows Systems · `win-04` → `win-08` | `win-04`의 Overlapped에서 출발한 completion 모델. "아무 스레드나 완료를 받는" 스레드 풀과, 그 때문에 생기는 순서 문제 |
| 5 | RIO | Windows Systems · `win-09` | 버퍼를 미리 등록하고, 요청과 완료를 큐로 주고받기 |
| 6 | `io_uring` | Linux Systems · `linux-04` | 커널과 공유하는 링 두 개. 시스템 콜 없이 요청하고 완료 받기 |
| 7 | 비교 | Operating Systems · `os-06` | 직접 만든 서버에서 `epoll`과 `io_uring`을 재본 결과 |

다음 편은 가장 오래된 `select`다. 왜 40년 넘게 살아남았는지, 그리고 왜 연결이 많아지면 버틸 수 없는지를 본다.
